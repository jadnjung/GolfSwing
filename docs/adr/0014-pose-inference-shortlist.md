# 0014. Pose-inference shortlist: react-native-fast-tflite + a vetted BlazePose model

- Status: Proposed (narrows ADR 0009's open question; not Accepted until real-device benchmarking, PRD section 23 Proof of Concept B, is actually possible)
- Date: 2026-08-03

## Context

ADR 0009 deferred picking a pose-inference library, rejecting `react-native-mediapipe` (cdiddy77) for staleness (last release 2024-12-12) and hand-written native modules for being unverifiable without a device. That ADR was written without network access to survey the landscape; this session has it, so re-checked what exists now.

Checked every realistic candidate:

- **`react-native-mediapipe`** (cdiddy77) — unchanged since ADR 0009: still 0.6.0, still last published 2024-12-12. Still fails this repo's maintenance bar.
- **`@gymbrosinc/react-native-mediapipe-pose`** — more recently published (1.0.8, 2026-01-08), but its `peerDependencies` list `expo: '*'`. Disqualified for the same reason ADR 0012 rejected `@expo/vector-icons` and the landscape-mode ADR (0013) rejected `expo-screen-orientation`: this project deliberately rejects managed Expo (PRD 7.4), and a required Expo peer is exactly that coupling, regardless of whether Expo APIs are actually invoked at runtime.
- **`react-native-mediapipe-posedetection`** (EndLess728) — newer-looking on the surface (New Architecture only, GPU acceleration, 33 landmarks, segmentation), but only 3 versions ever published, 23 total commits, 26 GitHub stars, single maintainer. Its own README documents "~15 FPS throttling to prevent memory issues" as a built-in workaround — a signal of real memory-management problems, not just thin adoption. Fails the same bar as cdiddy77's package, just more recently.
- **`@thinksys/react-native-mediapipe`** — most recently published of the wrapper options (0.0.21, 2026-04-10), clean peer dependencies (no Expo). But it ships its **own self-contained camera component** (`<RNMediapipe>`), not a `react-native-vision-camera` frame processor, and its README shows no API for running inference over an already-recorded video file. That's an architectural mismatch, not a maintenance one: PRD 8.2 makes post-processing over the *saved* swing video the primary pipeline ("use the saved video and process every frame"), with live inference a secondary, lower-quality guidance feature. A library that only knows how to process its own live camera feed can't drive that primary pipeline, and running two independent camera stacks (this app's existing `react-native-vision-camera` setup from ADR 0004, plus this library's own) side by side isn't a reasonable integration.
- **`react-native-fast-tflite`** (mrousavy — the same author as `react-native-vision-camera`, ADR 0004) — latest 3.0.1, published 2026-04-21, steady major-version cadence since 1.5.0 in late 2024. Clean peer dependencies (`react-native-nitro-modules`, already compatible with this project's New Architecture). It's a **generic TFLite runtime**, not a MediaPipe-specific wrapper: it runs whatever `.tflite` model file it's given, with GPU delegate support (Core ML/Metal on iOS, NNAPI on Android). The author's own tutorial (mrousavy.com) demonstrates exactly the live-guidance use case (a `react-native-vision-camera` frame processor feeding frames into a TFLite pose model, rendered via Skia) — but because it's not tied to a live camera feed at all, the same runtime can equally run inference over frames decoded from a saved video file for the post-processing pipeline PRD 8.2 actually needs most.

## Decision (proposed, pending real-device validation)

Shortlist **`react-native-fast-tflite` as the inference runtime**, paired with **a vetted MediaPipe BlazePose model file** (not MoveNet — see below), as the leading candidate to bring into PRD section 23's Proof of Concept B once real device access exists. Do not formally accept this as ADR 0009 would require — accepting still needs the actual latency/accuracy benchmarking on representative devices that PRD 16's Phase 0 exit criteria and `Checklist.md`'s "Pose-model benchmark" item call for, which this environment still can't do.

**Model choice within this approach:** BlazePose (33 landmarks, 3D world coordinates, per-landmark visibility, Apache 2.0 licensed) over Google's MoveNet (17 COCO-format keypoints, no depth, used in mrousavy's own tutorial) — BlazePose is the better fit for PRD POSE-002/003's actual requirements: MoveNet has no ankle/heel/toe distinction and no depth estimate at all, while PRD explicitly wants "feet or heel/toe points when supported" and "optional depth estimate." Bringing our own model file (rather than one bundled inside a wrapper library) also directly satisfies PRD 8.3's model-versioning requirements (our own semver, checksum, license, training-data description, evaluation report) — something no third-party wrapper's bundled model can promise on our schedule.

**Known open implementation question, not yet resolved:** current MediaPipe distributes BlazePose as a bundled `.task` file (a zip containing the raw `.tflite` plus metadata) via its Tasks API, not a bare `.tflite` file the way older MediaPipe Solutions releases did. Whether a `.task` bundle needs unpacking to extract a `react-native-fast-tflite`-compatible `.tflite`, or whether an older standalone BlazePose `.tflite` release is still available and license-compatible, needs to be confirmed as part of the actual Proof of Concept, not decided here without a device to test against.

## Consequences

- Doesn't change `Checklist.md`'s "Pose-model benchmark" status — that item stays unchecked until real iOS/Android device benchmarking happens, per PRD 16's exit criteria.
- Narrows Phase 2's eventual proof-of-concept work from "survey the whole landscape" to "benchmark this one shortlisted approach, with hand-written native modules as the documented fallback if it doesn't clear latency/accuracy bars" — meaningful time saved whenever device access actually arrives.
- If `react-native-fast-tflite` or the BlazePose model fails real benchmarking (PRD 8.4's accuracy/latency/subgroup criteria), fall back to the hand-written-native-module path ADR 0009 already scoped out, rather than re-surveying wrapper libraries whose fundamental gaps (staleness, Expo coupling, live-camera-only architecture) won't have changed.
- Revisit this ADR's status (Proposed → Accepted, or reject in favor of the fallback) once PRD section 23's Proof of Concept B actually runs.
