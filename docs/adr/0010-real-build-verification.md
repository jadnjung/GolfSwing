# 0010. Real build verification: Android debug build and iOS simulator build

- Status: Accepted
- Date: 2026-08-03

## Context

Every step since Step 2 (React Native app shell) has carried the same caveat: "not build-verified — no Xcode/Android Studio in this environment." Xcode and Android Studio were installed on this machine for the first time this session. This ADR records what it actually took to get a real `./gradlew assembleDebug` and a real `xcodebuild ... -sdk iphonesimulator build` to succeed — several genuine, previously-invisible bugs, not just environment setup.

## Decisions and fixes

### 1. `@react-native/gradle-plugin` and `@react-native/codegen` were never wired into `apps/mobile`

`apps/mobile/android/settings.gradle` (generated by the RN CLI template in Step 2) does `includeBuild("../node_modules/@react-native/gradle-plugin")`, and RN's own codegen tasks `require` `@react-native/codegen` at build time. Both packages exist in the pnpm store as transitive dependencies of `react-native` itself, but pnpm's strict per-package `node_modules` isolation means a transitive dependency of `react-native` is not reachable from `apps/mobile/node_modules/@react-native/` unless `apps/mobile` depends on it directly. Neither had ever been exercised before, because no build had ever reached the Gradle configuration/codegen stage. **Fix:** added both as explicit `devDependencies` in `apps/mobile/package.json`.

### 2. `react-native-screens` 4.26.x doesn't build against this project's RN/codegen version

4.26.0 introduced an experimental "gamma" stack-header native component (`StackHeaderConfigAndroidNativeComponent.ts`) whose `NativeCommands` spec uses `React.ComponentRef<>`. RN 0.81.6's `@react-native/codegen` TypeScript parser only understands the older `React.ElementRef<>` for native command refs, and fails with `Error: The first argument of method setToolbarMenuElementOptions must be of type React.ElementRef<>` — for a component this app never uses, but codegen parses every spec file in an installed library regardless of usage. Checked whether a newer patch fixed it (no — 4.26.2 is still latest stable, same bug) and whether a peer-compatible option existed: 4.25.0 has this file with a *different*, smaller `NativeCommands`-free shape, but declares `peerDependencies: { "react-native": ">=0.82.0" }` — incompatible with this project's pinned 0.81.6 (ADR 0003). **Fix:** pinned `react-native-screens` to `4.24.0` — predates the gamma stack-header file entirely, has no `ComponentRef` usage anywhere in its native specs, and declares `peerDependencies: { "react-native": "*" }` (verified directly against the downloaded tarballs for 4.24.0/4.25.0/4.26.0, not assumed). Revisit via a new ADR once a `react-native-screens` release both fixes the codegen incompatibility and is verified against RN 0.81.x.

### 3. CocoaPods belongs in `apps/mobile/Gemfile`, not the repo-root `Gemfile`

Step 1 (ADR 0002) deferred adding CocoaPods to the **root** Gemfile with the reasoning "there is no `ios/Podfile` yet." That was accurate at the time, but Step 2 (React Native app scaffolding) already generated `apps/mobile/Gemfile` via the RN CLI template — a Gemfile that pins CocoaPods with specific version exclusions (`!= 1.15.0`, `!= 1.15.1`) for releases known to break RN builds, plus compatible `activesupport`/`xcodeproj`/`concurrent-ruby` pins. This session's first attempt added `cocoapods` to the root Gemfile instead, missing that the app-scoped one already existed — reverted once `bundle exec pod install` from the repo root failed to resolve CocoaPods cleanly and the actual template Gemfile was found. **Fix:** run `bundle install`/`bundle exec pod install` from `apps/mobile` (its own `Gemfile.lock`, `vendor/bundle/` gitignored), leaving the root `Gemfile` unchanged with its Step 1 reasoning intact — that reasoning was about the *root* Gemfile specifically and remains correct.

### 4. `pod install`'s autolinking step needs the fnm-managed Node active in the same shell

CocoaPods' `use_native_modules!` shells out to a bare `node -e ...` command to discover native modules via `@react-native-community/cli`. If a stale system Node is first on `PATH` (this machine had `/usr/local/bin/node` v20.18.0, below RN's `engines.node` minimum of `>=20.19.4`), autolinking fails with a generic `returned a status code of 1` — CocoaPods doesn't surface the underlying Node error, and reproducing the exact failing command manually (with the correct Node active) succeeds, which is misleading until you check `which node`/`node --version` in the exact shell running `pod install`.

### 5. Stale Gradle daemons keep a build's original (wrong) environment

The first `./gradlew assembleDebug` attempt ran without `fnm`'s Node active, so Gradle's codegen task shelled out to system Node (v20.18.0) and failed on a missing module. After fixing the environment (adding `@react-native/codegen` as a dependency, activating fnm), the **same error persisted** on retry — because Gradle's daemon, once started, keeps running with the environment it was launched under, and `./gradlew` reuses that daemon by default. **Fix:** `./gradlew --stop` before retrying after any environment change, not just re-running the build.

### 6. `fmt` 11.0.2's `consteval` codepath miscompiles under Xcode 26.6's Clang

The iOS simulator build failed with `error: call to consteval function ... is not a constant expression` in `fmt/format-inl.h` (`fmt` is a transitive dependency via `glog`/`hermes-engine`). `fmt/include/fmt/base.h` unconditionally enables `FMT_USE_CONSTEVAL` for any Clang reporting itself as version ≥ 11 (`FMT_CLANG_VERSION >= 1101`) or exposing `__cpp_consteval` — both true for Xcode 26.6's Clang — but that codepath doesn't actually compile cleanly with this specific Clang release. Verified the fix (`#define FMT_USE_CONSTEVAL 0`, bypassing the whole detection block) directly by patching the vendored `Pods/fmt/include/fmt/base.h` and rebuilding before committing to it. **Fix:** added a `post_install` hook to `apps/mobile/ios/Podfile` that applies this same patch automatically after every `pod install` — `Pods/` is gitignored and fully regenerated each time, so the fix has to live in the Podfile, not as a one-off edit to vendored source.

### 7. `pod install` enables React Native's New Architecture by default

Diffing the Xcode project after `pod install` showed `RCTNewArchEnabled = true` added to `Info.plist`, plus `USE_HERMES = true` and a `REACT_NATIVE_PATH` build setting added to `project.pbxproj` — none of these were set explicitly anywhere in this repo. RN 0.81's `prepare_react_native_project!`/Podfile helpers default new projects to the New Architecture (Fabric + TurboModules) unless explicitly opted out. This also explains why codegen ran so extensively during these builds (New Architecture requires it for every native module, not just ones that opt in) — it's RN 0.81.6's own default behavior, not a misconfiguration, but worth recording since nothing in `docs/adr/0003-react-native-version.md` called it out as a deliberate choice.

### 8. Real bug found only by actually running the app: no screen used safe-area insets

Installed the built iOS app on a booted `iPhone 17` simulator (`xcrun simctl install`/`launch`), started Metro, and screenshotted it — this is the first time any screen in this app has actually been seen rendering. The onboarding privacy screen's title was overlapped by the status bar/notch: despite `SafeAreaProvider` being wired at the root since Step 2, **no screen anywhere in the app actually consumed it** — every screen used a plain `View`/`ScrollView` as its root container. This wasn't visible in any Jest test, because `react-test-renderer` doesn't render real layout/insets. **Fix:** switched every screen's root container to `SafeAreaView` from `react-native-safe-area-context` (`ScreenContainer.tsx` — shared by Home/Settings/Training; `HistoryScreen.tsx`; `RecordScreen.tsx`; `OnboardingScreen.tsx`), using `edges={['top']}` for screens under the bottom tab navigator (which already handles the bottom inset for its own bar) and both `top`/default edges for `OnboardingScreen` (no tab bar underneath it). `ReplayScreen` was already fine — it renders under a native-stack header, which react-navigation already insets correctly. Re-verified by rebuilding and re-screenshotting: the title now sits cleanly below the status bar.

## Consequences

- `./gradlew assembleDebug` succeeds (`apps/mobile/android/app/build/outputs/apk/debug/app-debug.apk` produced) and `xcodebuild ... -sdk iphonesimulator build` succeeds against the `iPhone 17` simulator — the first real build verification since Step 2.
- The built iOS app was actually installed and launched on a booted simulator and screenshotted twice (before and after the safe-area fix) — the first real *runtime* verification of any screen in this app, not just a successful compile.
- `docs/architecture/toolchain.md` updated with per-machine setup notes (JDK 17 without `sudo`, stale-daemon gotcha, which Gemfile to use) so the next session doesn't have to re-derive this.
- The `react-native-screens` pin (`4.24.0`, down from `^4.26.2`) means missing out on two minor releases' worth of fixes/features unrelated to the gamma stack header — acceptable given none of this app's screens use that experimental API. Revisit once upstream fixes the codegen incompatibility.
- The `fmt` consteval patch is inherently fragile — it pattern-matches specific source text in a vendored header and warns (via `Pod::UI.warn`) rather than silently no-op'ing if a future `fmt` version changes that text. If `fmt` upstream fixes the actual Clang-version detection, this patch becomes unnecessary and should be removed via a new ADR rather than left in indefinitely.
- Every screen now actually respects safe-area insets — a real, previously-invisible bug fixed as a direct result of this verification effort, not something a build success alone would have caught.
- Still not verified: a physical device (only the simulator), and Android's runtime behavior specifically (only its build was verified end-to-end; the iOS side got the actual install+launch+screenshot treatment since the Android emulator wasn't set up this session — no system image installed yet).
