## Getting a real build running (per-machine setup, not committed to the repo)

None of this is automated — it's what actually made `./gradlew assembleDebug` and `pod install` succeed on this machine, kept here so the next person (or session) doesn't have to re-derive it:

1. **JDK 17**: Android Studio's bundled JBR is a much newer major version (25 at time of writing) than this project's JDK 17 pin, and Homebrew's `openjdk` cask needs `sudo` to install. Downloaded a Temurin 17 tarball directly (Adoptium's API) to `~/.jdks/jdk-17.0.20+8`, no `sudo` needed — set `JAVA_HOME` to its `Contents/Home` before running `./gradlew`.
2. **Android SDK components**: the Android Gradle Plugin auto-installs missing SDK platforms/build-tools itself on first build (it fetched Android SDK Platform 36 and Build-Tools 35 automatically) — no manual `sdkmanager` step was needed, despite only platform 37 being present after a fresh Android Studio install.
3. **Stale Gradle daemon**: a Gradle daemon started with the *wrong* environment (before `JAVA_HOME`/Node were correctly set) keeps reusing that environment across builds until stopped — run `./gradlew --stop` after fixing environment variables, not just re-run the build.
4. **CocoaPods**: install via `apps/mobile/Gemfile` (`cd apps/mobile && bundle install`), not the repo-root `Gemfile` — the RN CLI template already generated an app-scoped Gemfile in Step 2 with version exclusions for known-broken CocoaPods/activesupport/xcodeproj releases; the root Gemfile's own Step 1 deferral note about CocoaPods was correct to leave alone.
5. **`pod install` needs the fnm-managed Node active in the same shell** — CocoaPods' autolinking step shells out to plain `node`; if a stale system Node is first on `PATH` (below RN's `engines.node` minimum), autolinking fails with a generic "returned a status code of 1" that doesn't surface the underlying Node error.
6. **Android emulator**: Android Studio's install does *not* include a standalone `sdkmanager`/`avdmanager` — download Google's `commandlinetools-mac-*_latest.zip` separately and extract to `~/Library/Android/sdk/cmdline-tools/latest`. From there: `sdkmanager --licenses`, `sdkmanager "system-images;android-34;google_apis;arm64-v8a"`, `avdmanager create avd --name <name> --package "system-images;android-34;google_apis;arm64-v8a" --device pixel_7`, then `emulator -avd <name>`. The emulator doesn't share the host's `localhost` — run `adb reverse tcp:8081 tcp:8081` before launching the app, or Metro's dev server won't be reachable. The AVD created this way is named `golf-swing-test` (already exists on this machine — no need to recreate it, just `emulator -avd golf-swing-test`).
7. **`bundle`/`pod install` needs rbenv's Ruby active, not the system one**: macOS ships Ruby 2.6.10 at `/usr/bin/ruby`, but `apps/mobile/Gemfile.lock` pins Bundler 2.7.2, which refuses to run under Ruby < 3.2. `rbenv` (already installed via Homebrew, `.ruby-version` at the repo root already pins 3.3.12) has the right Ruby *and* Bundler 2.7.2 already available through its shims — no `gem install` needed. The fix is purely `PATH` ordering: `eval "$(rbenv init - bash)"` alone did not reliably win over `/usr/bin` in a non-interactive shell in this environment; explicitly run `export PATH="$HOME/.rbenv/shims:$PATH"` before `ruby -v`/`bundle exec pod install` and confirm with `which ruby` that it resolves to `~/.rbenv/shims/ruby`, not `/usr/bin/ruby`.
8. **Android emulator camera can be flaky across restarts**: the `golf-swing-test` AVD's emulated back camera (`hw.camera.back = emulated` in its `config.ini`) worked correctly the first time a build was installed and launched, but failed to enumerate ("No available camera can be found" in `adb logcat`, from `androidx.camera.core.impl.CameraValidator`) on later cold-boot attempts in the same session, even after a full `emulator -no-snapshot` restart and re-granting the `CAMERA` permission. This reproduced with no app-code changes in between — treat it as an emulator/CameraX quirk to retry past (fresh AVD, `-camera-back emulated` explicit flag, or just retrying), not a real bug to chase in this app's code, unless it reproduces on a physical device too.
9. **iOS Simulator has no scriptable tap/touch command**: `xcrun simctl` can install, launch, and screenshot an app, but has no equivalent to Android's `adb shell input tap`. Driving multi-step UI interaction (tapping through onboarding, etc.) needs either a physical device, or macOS Accessibility permission for `osascript`/System Events to control the Simulator window — which this environment does not have granted (`osascript ... System Events` fails with `-1719, not allowed assistive access`). Don't spend time retrying System Events automation without first confirming Accessibility access is actually grantable in the current environment; fall back to install+launch+screenshot-only verification on iOS, and drive fuller interaction on Android instead where possible.
